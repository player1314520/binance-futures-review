# Binance 合约复盘助手

这是网页版主产品的公开邀请制 Beta 候选：面向个人 Binance USDⓈ-M 合约交易者，把“只读同步/导入证据 →
覆盖与对账 → 逐笔复盘 → 下一步动作 → 每日记录与风控护栏 → 周报/月报 → 灾备恢复”收在一个闭环里。
产品会接收专用只读 Binance API Key/Secret，但拒绝交易、转账和提现权限，也没有下单、改单、撤单或资金划转接口。
当前状态仍是 `not_distributed`，源码候选不等于 Tokyo 后端或完整生产站已经上线。

## 产品工作流

1. 受邀用户登录，重新确认 v5 数据处理方式，再连接独立的 Binance USDⓈ-M 只读 Key。
2. Key/Secret 会发送到 Edge 服务验证权限，并以每连接随机 DEK + AES-256-GCM 加密保存；拥有包装密钥的
   管理员和部署环境理论上能够解密。
3. 云同步把规范化交易、覆盖、Ledger、复盘、行动、日志、风控和报告写入服务端数据面；这些业务数据
   不是端到端加密，服务端可以读取。任何 `PARTIAL / STALE / UNKNOWN / CONFLICT` 都继续锁住账户级指标。
4. Binance CSV 仍在浏览器本地完成解析和边界检查；它只能补充覆盖证据，不能冒充交易所完整总账。
5. 工作区删除、全部业务数据清除和账户删除是三条独立路径；每条都有幂等回执和响应丢失后的状态对账。
6. Classic 复盘可从同源旧存储或只读 JSON 导出进入预览；默认全不选，只按当前数据集内完全相同的
   Trade ID 插入且不覆盖已有复盘。旧端到端加密 vault 强制只读，只能由用户在浏览器显式解密后迁移，
   禁止双写和反向覆盖；旧风险参数只展示，不自动改写新守则。

复盘产生的下一步动作不是一个可随手勾掉的待办：用户先定义单变量假设、日期窗口、目标次数和成功标准，
逐次记录是否执行及证据，达到样本数后才选择保留、修改重测或放弃。周报/月报之外还可应用最长 366 天的
任意日期范围；完整备份可恢复成交账本、复盘、实验、日志和守则。
只有 `full-workspace` 完整备份能替换离线工作区；日期范围 envelope 失败关闭。Demo 恢复后仍标记为合成演示，
Binance 备份不包含 API 凭据，恢复后必须重新连接。服务端日备份排除 Key/Secret、DEK、包装密钥、Auth Secret
和临时下载链接，再使用离线 age 公钥加密；删除 tombstone 必须先于恢复应用，防止备份复活已删除用户。

桌面端提供 17 个工作入口：今日速览、复盘总览、复盘卡、归因对标、市场情境、R 复盘、策略手册、
今日仪式、交易日历、K 线回放、AI 教练、行为实验室、周报月报、对比复盘、成长目标、深度洞察、
数据中心。移动端首屏保留四个高频入口，并通过“更多”菜单完整开放同一组 17 个入口，数据和闭环状态与
桌面网页版一致。

## 隐私与安全

- 登录采用邀请制；公开网页只接受项目的 Supabase URL 与 publishable key，不允许 service-role 或管理密钥。
- 邀请 Beta 的 Binance Key/Secret 由服务端加密保存，交易与复盘数据服务端可读；这不是零知识或端到端加密。
  包装主密钥不得进入数据库、Vercel、GitHub、R2、Brevo、浏览器或日志，部署权限按可解密权限管理。
- 旧端到端加密 vault 只作只读迁移与回滚源；它的历史恢复密钥不用于保护新 Beta 数据面。
- 页面使用严格 CSP：网络连接只允许同源和配置的单一 Supabase HTTPS origin，不允许内联脚本或动态执行。
- 公开候选由精确白名单导出，不包含 `.env`、真实交易文件、`app/dist`、缓存、日志、私有 Git 历史或
  服务端密钥。候选公开当前生产 SQL、`delete-account`、`publish-vault-head`、`binance-beta`、`restore-v2`、
  `beta-operations` 的无秘密运行时代码、部署手册和对应测试，方便交付方复核并重新部署。

## 本地验证

```text
pnpm install --frozen-lockfile
pnpm verify
```

`pnpm verify` 会在 Node/Vitest 门禁之外启动真实 Chromium，检查生产构建响应头与 CSP、指标证据锁、
17 个桌面入口、390px 移动布局、复盘/日志/守则/报告、完整备份下载与未解锁恢复拒绝，并在浏览器中执行
PBKDF2 600,000 次、AES-GCM、Ed25519、恢复文件和 OTP 客户端回路。

GitHub Pages 工作流只部署 `public-site/index.html` 的无数据入口页。完整应用由根目录 `vercel.json` 构建到
独立 Vercel origin；`release-config.ts` 要求生产构建绑定完整提交、精确 Supabase ref、独立应用 origin 与
双用户 live-gate 回执，并生成可在线核对的 `release.json`。任何候选导出、推送、计费或部署仍需单独授权。

## 诚实边界

1. CSV 只能证明文件中存在的记录，不能自动证明账户历史完整、手续费齐全或已与 Binance 总账对平。
2. 新 Beta 不是端到端加密：管理员或被攻陷的部署环境理论上能够解密 Binance 凭据并读取交易与复盘数据。
3. Supabase Edge 没有固定出口 IP，不能启用 Binance IP 白名单；小时级同步是尽力目标，不是实时 SLA。
4. GitHub Pages 只是无数据入口，不能作为登录生产站；Vercel 响应头也不能替代持续的 WAF、限流和配置漂移检查。
5. 规则型“AI 教练”只基于用户自己的复盘字段给出确定性提示，不读取市场未来，也不提供交易信号或收益承诺。
6. 自动测试与合成数据不能证明真实账户同步完整、真实网络可用或未来交易结果；产品不构成投资建议。
7. 公开 Chromium 门禁使用本地构建和模拟认证响应；真实邀请登录、RLS、Edge Function、跨用户隔离与删除
   仍必须在全新隔离 Supabase 项目的双用户 live gate 中通过，不能由浏览器烟测替代。
8. 浏览器同源策略阻止新版直接读取其他域名或端口的 Classic 存储；没有完全相同 Trade ID 的旧记录不会
   近似迁移。行为实验只能验证用户记录的动作执行率，不能证明该动作改善收益或具有市场因果性。
9. 已经打开的旧版本标签页不理解新版事务协议；升级后必须刷新所有旧标签页，再执行 Classic 迁移、完整恢复
   或浏览器隐私清除。
10. 浏览器写入、迁移、恢复和清除需要 Web Locks API；不支持时会安全拒绝，不会退回非原子的
   `localStorage` 租约。当前真实浏览器交付基线为现代 Chromium。
